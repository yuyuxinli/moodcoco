当前结论

  • STT服务端 final 很快，约 0.15s，不是主要瓶颈。
  • LLM首句生成慢，p50 约 6.04s，是当前体感等待的核心来源。
  • TTS多数轮次约 0.3s，但第一轮出现 3.38s，需要继续观察连接或首包波动。

当前链路

Web mic 进入 LiveKit，worker 使用 Xfyun streaming STT 产出 partial/final， `VoiceStreamingResponder` 调 OpenAI-compatible LLM 按句切分，MiniMax WebSocket TTS 输出 PCM， 再通过 LiveKit `AudioSource` 推回浏览器。

质量观察

最新评测中 Coco 回复存在重复字和异常片段，例如“很很难很定”“现现”。这不只影响听感，也会让用户觉得回复不聪明。

主要瓶颈

最大耗时来自 `user_final -> first_coco_sentence`。这段包含 LLM 请求、模型首 token、句子切分到首句可播出的过程。 当前还没有把上下文和 carryover 优化落到最新验收，因此“聪明程度”和“上下文能力”也会受限。

为什么 STT 看起来也慢

“有效语音 -> user_final”包含用户实际说话时长和尾静音 endpoint，所以会有 5-6s。 真正的 STT 服务 final 延迟应看 `endpoint -> user_final`，当前 p50 只有 154ms。

下一步建议

先做 voice context 和 carryover，让回复更像连续对话；同时加 LLM 首 token/首句指标。 在能区分 LLM 首 token慢还是切句慢之后，再优化首句延迟。重复字问题需要单独定位来源。
