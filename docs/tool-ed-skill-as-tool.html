TOOL-ED

把共情技能建模为 Tool Call：LLM 情绪对话的新范式
COLING 2025 Cao, Zhang, Feng et al. EKTC Framework arXiv: 2412.03096

30 秒版本

传统做法：把心理咨询技能写进 system prompt，让 LLM 自行判断何时使用。问题是要么每轮都用（引入噪声），要么根本不用。 TOOL-ED 的核心洞察：把共情知识库封装为标准 tool schema，让 LLM 像调 API 一样按需调用。 模型自己学会了只在 26% 的对话轮次调用 tool——不是每轮都查，也不是完全不查，而是根据用户情绪强度和上下文自适应决策。 GPT-4 评估：共情 71% win，一致性 86% win，流畅度 87% win。

关键设计：模型在训练数据中只有 26.46% 的轮次包含 tool call。这意味着模型必须自己学会何时调用、何时不调用——而不是规则触发。

Tool 定义方式：把知识库封装为 Tool Schema

TOOL-ED 的核心创新不在于知识库本身，而在于如何把知识库包装成 LLM 可理解、可调用的 tool 接口。两个知识库被定义为一个统一的 tool：

// EmotionKnowledgebase Tool Definition
{
  "name": "EmotionKnowledgebase",
  "description": "查询情绪相关的常识知识库，
    获取用户可能的意图、需求、期望、
    行为后果、情绪反应等推理信息",
  "parameters": {
    "type": "object",
    "properties": {
      "dialogue_context": {
        "type": "string",
        "description": "当前对话上下文 C"
      }
    }
  },
  "returns": {
    // observation = COMET(C) + CICERO(C)
    "xIntent": string,  // 用户意图
    "xNeed": string,    // 用户需求
    "xWant": string,    // 用户期望
    "xEffect": string,  // 行为影响
    "xReact": string,   // 情绪反应
    "Cause": string,    // 因果关系
    "SubEv": string,    // 后续事件
    "Motiv": string,    // 动机
    "React": string     // 反应
  }
}

COMET 基于 ATOMIC2020

xIntent "他可能想要被理解"
xNeed "他需要先冷静下来"
xWant "他希望有人倾听"
xEffect "他可能会更焦虑"
xReact "感到沮丧和无助"

CICERO 对话常识

Cause "因为工作压力太大"
SubEv "接下来可能会请假"
Motiv "他想要改变现状"
React "对方会感到被关心"
注意：TOOL-ED 并不是把"倾听""共情""认知重评"这些咨询技能直接定义为 tool。它把常识推理能力定义为 tool——让模型在需要时获取关于用户意图/需求/因果的推理信息，然后用这些信息生成更好的共情回复。

调用机制：ReAct 格式的自适应 Tool Call

推理时，模型遵循 ReAct (Reasoning + Acting) 格式，在两种输出模式之间自主切换：

示例：用户说 "我被裁员了，不知道该怎么办"
Thought: 用户表达了强烈的负面情绪（焦虑+迷茫），需要理解其深层需求和可能的后续影响
Action: EmotionKnowledgebase
Action Input: {"dialogue_context": "用户: 我被裁员了，不知道该怎么办"}
Observation: xIntent: 寻求安慰和方向 | xNeed: 经济安全感 | xReact: 恐惧、自我怀疑 | Cause: 公司裁员 | SubEv: 可能开始找新工作
Response: 被裁员的冲击一定很大。失去工作不只是收入的问题，也会让人对自己的价值产生怀疑。你现在最需要的可能不是马上行动，而是先让自己稳下来...
示例：用户说 "嗯，说得对"
Response: 你想多聊聊现在的感受，还是我们一起想想下一步可以做什么？
(模型判断这个上下文不需要外部知识，直接回复，不调用 tool)

关键发现：Tool-call 比例 ~26% 是模型自学的。强制每轮调用反而降低质量——选择性调用优于全量调用，这验证了"按需取用"的直觉。

对 moodcoco 的价值

可借鉴：Skill-as-Tool 范式

  • Skill routing 用 tool call 而非 prompt instruction：把每个咨询技能（倾听、认知重评、情绪命名...）定义为 tool schema，模型通过 function_call 结构化调用。比"请根据情况选择合适的技能"的 prompt 更可控、可观测
  • 自适应调用率是对的方向：不是每轮都需要"施展技能"，大部分时候安静倾听就够了。26% 的调用率与真实咨询场景吻合
  • 可审计的 skill trace：每次 tool call 都有记录，可以做质量回溯——"这次对话调了哪些技能、效果如何"
  • 即插即用扩展：新增一个技能只需要定义 tool schema + 实现后端，不需要改 system prompt

需改造：TOOL-ED 的 tool 不是咨询技能

  • TOOL-ED 的 tool = 常识知识库查询，本质是 RAG；moodcoco 需要的 tool = 咨询行动（倾听/共情/认知重评/安全转介）
  • TOOL-ED 的 tool 返回知识（用户可能在想什么）；moodcoco 的 tool 应该返回行动指令（用什么方式回应）
  • moodcoco 如果要用这个范式，需要把 ESConv/MITI/Hill 的技能编码系统映射成 tool schema

局限性

论文自述局限

  • 单 tool 限制：只定义了一个 EmotionKnowledgebase tool，不支持多 tool 协调。真实咨询需要多技能组合使用
  • 知识库边界：COMET/CICERO 是通用常识，缺乏心理学专业知识（如 CBT 认知扭曲、依恋理论等）

我们观察到的局限

  • 评估偏差：用 GPT-4 评"共情"本身就有问题——GPT-4 的共情标准和心理咨询师的标准不一样
  • 不是真正的 skill selection：模型选择的是"查不查知识库"，不是"用哪种咨询技能"。这是一个二值决策，不是多技能路由
  • 数据集偏差：EmpatheticDialogue 是众包对话，情绪深度有限；26% 的调用率可能反映的是数据集的浅层对话偏多
  • 缺乏跨轮记忆：每次 tool call 独立，不跟踪用户跨轮的情绪变化模式
  • 延迟代价：每次 tool call = 知识库推理 + 额外一轮 LLM 生成。在语音场景（moodcoco 的核心）中，这个延迟可能不可接受
语音场景适配风险：TOOL-ED 的设计基于文本对话。在 moodcoco 的 fast/slow 架构中，tool call 引入的额外延迟需要仔细评估。可能只适用于 slow path，fast path 仍需 prompt-based 方案。

Reflector 的三重一致性检验：

  • 因果一致性 (Causal)：tool 返回的原因推理与 golden response 的因果逻辑一致
  • 意图一致性 (Intent)：tool 推断的用户意图与 golden response 的回应方向一致
  • 情绪一致性 (Emotional)：tool 推断的情绪状态与 golden response 的情绪匹配
