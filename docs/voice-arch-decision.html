moodcoco Voice Agent 技术方案 v3

Speaker + Thinker 架构 · VAD 触发（LiveKit 默认）· Cross-turn Only
2026-05-13 分支: feat/fast-slow-sjtu-fusion 基座: LiveKit Agents SDK + pydantic-ai
核心原则：最简单、最成熟的方案先上。没有 LLM 分类触发、没有 Gate、没有 same-turn mutation。所有高级能力（语义打断、状态分类、全双工）留给有 GPU + 训练数据时再做。

整体架构

Speaker 永远先完成（Doubao Lite 快）, Thinker 永远后完成（Minimax m2.7 + 记忆 API 慢） 2. 所有 Thinker 输出都是 cross-turn: 写入 deps → 下一轮 Speaker 读取 3. 不存在 same-turn mutation（Thinker 比 Speaker 慢，不可能同轮改 Speaker 行为） 4. 4 状态生命周期: Idle → UserSpeaking → Processing → AIResponding
不引入新基础设施。所有改进在现有 LiveKit + pydantic-ai 同进程架构内完成。Thinker 走 API 调用（Minimax m2.7），不需要分布式部署、不需要 GPU。
1
Speaker/Thinker 并行机制
优化现有
决策
Typed Protocol + 现有共享对象，不做分布式拆分。Thinker 走 API。
现有 deps mutation 上层加 Pydantic Model 做 typed protocol Speaker/Thinker 同进程通信，延迟 ~0ms Thinker 走 API（Minimax m2.7），无需独立 GPU 部署 未来若需分布式，protocol 层已定义好，只换传输层
为什么不选 Event Bus（VoiceAgentRAG）或 LiveKit Data Channel（Stimm）： Thinker 走 API 调用而非本地推理，分布式部署是伪需求。Event Bus 多 5-15ms 延迟 + 新基础设施，Data Channel 多 2-5ms + 架构复杂度，收益为零。
参考: Stimm StimmProtocol 消息类型设计 参考: LTS JSON State Schema
2
触发机制
LiveKit 默认
决策
纯 VAD 触发（LiveKit 默认行为），无 LLM 分类，无 Gate
触发方式: Silero VAD 检测到用户停止说话（静音） → 同时触发 Speaker + Thinker → Speaker 生成回复 → 中途没有新语音进来 → 发出去 → 有语音进来 → 停止 Speaker，等用户说完，重新触发 状态机: 只有 4 个状态，全部由 VAD 驱动 Idle → UserSpeaking → Processing → AIResponding (无 LLM 参与触发判断)
状态VAD 事件动作
Idle检测到语音→ UserSpeaking
UserSpeaking检测到静音→ Processing（触发 Speaker + Thinker）
ProcessingSpeaker 开始 TTS→ AIResponding
AIRespondingSpeaker 完毕 / 用户出声→ Idle / UserSpeaking（停止 Speaker）
为什么不用 LLM 做状态分类（6 状态）：业内没有用 API LLM 做 0.6s 轮询状态判断的成功案例。DuplexCascade 用 LoRA 微调本地模型，LTS 用 DistilBERT 5ms 分类器 — 都需要 GPU + 训练数据，我们目前不具备。
为什么不加 Gate：Gate 存在的唯一理由是 0.6s 轮训判断用户状态（思考/说完/哭泣），但没有本地小模型就不可能做到。用 API LLM 轮询每分钟 ~100 次调用，成本不可接受。
LiveKit 默认行为已足够：VAD 二值判断（说话/静音）是最成熟、最广泛使用的触发机制。高级状态判断作为未来升级。
采用: LiveKit Agents SDK 默认 VAD 行为
未来升级（需 GPU + 训练数据）：LTS 式 DistilBERT 语义完整度分类器（5ms），替代 VAD 静音门。可区分 user_finished / user_thinking / user_crying 等 6 种状态。
3
Context 预热
新增
决策
Thinker 顺带输出 next_likely_contexts + 用户记忆驱动预测 + Context 预组装
Thinker 每轮输出 schema: { emotion: "...", skill: "untangle", // skill 是 Context 的一部分 guidance: "...", next_likely_contexts: ["decision(纠结)", "calm-body(焦虑)"] } 预热动作（同步，~0ms）: → 拼好 decision 的 prompt 模板 + 用户记忆 + 当前情绪 → 拼好 calm-body 的 prompt 模板 + 用户记忆 + 当前情绪 → 存入 deps.prewarmed_contexts 下一轮: → Thinker 判断 context = decision → 命中 → Speaker 直接用预热 context → Thinker 判断 context = listen → 未命中 → 正常流程
为什么不做 VoiceAgentRAG 式语义缓存：他们缓存的是向量数据库检索结果（文档），我们没有向量库。我们的瓶颈不是检索延迟，是 Thinker LLM 调用时间。
预测依据：用户记忆中的历史 context 轨迹（通过外部记忆模块 API 获取）+ 当前 session 的 context 序列。不是瞎猜。
零额外 API 调用：预测是 Thinker 输出 schema 的一个字段，不需要单独调 LLM。
核心参考: VoiceAgentRAG "LLM 预测后续话题"思路 参考: VoiceAgentRAG Semantic Cache 架构（检索场景，未直接采用）
4
打断处理
LiveKit 默认
决策
用户出声 → 统一停止 Speaker（LiveKit 默认行为），不区分附和/打断/补充
AI 正在说话 + 用户出声 → VAD 检测到 → 停止 Speaker（整个停，不是停 TTS） → 等用户说完 → 重新触发 Speaker + Thinker 不区分： · "嗯" (附和) → 停止 Speaker · "不对" (打断) → 停止 Speaker · "而且..." (补充) → 停止 Speaker → 全部统一处理，最简单
为什么不做语义区分：DuplexCascade 的 backchannel/interrupt/supplement 区分需要 LoRA 微调本地模型做 0.6s 轮训判断。API LLM 做不到这个速度。
为什么 LiveKit 默认够用：情绪陪伴场景下，多打断几次（把附和误判为打断）的体验损失远小于不打断（把打断误判为附和继续说）的体验损失。保守策略更安全。
采用: LiveKit 默认打断行为
未来升级（需 GPU + 训练数据）：DuplexCascade 式语义打断判断，区分"嗯"（附和，Speaker 继续）vs 真打断（停止 Speaker）vs 补充（拼入当前轮）。LTS Thought Rollback（Speaker 被打断后 Thinker 结果复用）。
5
全双工能力
暂不需要
决策
半双工 + 打断即停。AI 说话时能听到用户，但统一停止处理。
AI 说话时能听到用户 ✅ · 打断即停 ✅ · 双方同时语义输出 ❌（不需要）
真全双工（DuplexCascade）需要 LoRA 微调本地模型 + 0.6s 微轮次，不在当前技术栈可达范围内。
6
Thinker → Speaker 通信 + 注入
优化现有
决策
3 种 mutation 通道 + next_likely_contexts，全部 cross-turn，单向 Thinker→Speaker
Thinker → Speaker 注入方式（Pydantic Model 约束）: 1. dynamic_inject — 短指导语，跨轮 LRU 保留 3 条 2. skill_bundle — 完整 skill prompt (SKILL.md)，跨轮 LRU 保留 2 个 3. retrieval_block — ≤200 字摘要，跨轮保留最新 1 条 4. prewarmed_contexts — 预组装的 Context（新增） 所有写入都是 cross-turn: 本轮写入 → 下一轮 Speaker 读取 Speaker 读取方式: · @instructions hook → 编译为 system prompt · 检查 prewarmed_contexts 是否命中 Speaker → Thinker: 无直接信号 · Thinker 通过读取 ASR 文本 + deps 上下文获取信息
为什么单向（Thinker→Speaker）：VoiceAgentRAG 有 cache miss 事件（Fast→Slow），Stimm 有 4 种上行消息，但它们的 Slow 管知识（需要 Fast 反馈"缺什么"）。我们的 Thinker 管行为（Context），不需要 Speaker 反馈。
参考: Stimm StimmProtocol 5 下行 + 4 上行消息类型 参考: LTS Thinker JSON State 结构化输出
7
记忆 + RAG
暂不动
决策
记忆模块在独立项目中，moodcoco 只通过 API 调用。RAG 后续与记忆结合。
记忆是跨产品能力，不耦合在 voice agent 内。moodcoco 需要用户记忆时（如 next_likely_contexts 的历史 context 轨迹），通过外部记忆模块 API 获取。向量 RAG 在情绪陪伴场景暂无检索对象（无文档知识库），等记忆模块就绪后再整合。
8
情绪识别 / 技能路由
保持优势
决策
保持现有 6 种 skill 路由，Thinker 核心职责是 Context 控制（skill 是 Context 的一部分）
crisis / calm-body / decision / untangle / relationship / listen — 业内无人做到这个粒度。DuplexCascade 仅识别"沉思"，Stimm 仅有安全过滤潜力，其余方案不涉及情绪。这是 moodcoco 的核心护城河。
重要澄清：Thinker 的核心职责是控制 Context，skill 只是 Context 的一部分。Thinker 还输出情绪判断、guidance、预测等。不应把 Thinker 理解为"skill 路由器"。
9
发言前安全过滤
新增
决策
三层防护：Speaker prompt 约束 + 关键词过滤 + Thinker 异步追溯修正
第 1 层: Speaker system prompt 内置安全红线（0ms） · 不诊断、不替用户做决定 · 不对不在场的人做动机判断 · crisis 场景引导专业求助 第 2 层: 关键词/正则兜底（~0ms） · 极端有害内容过滤（黑名单） 第 3 层: Thinker 异步追溯（不阻塞） · Thinker 审查 Speaker 的输出内容 · 发现灰色地带问题 → 下一轮修正/补充 · 如 Speaker 给了不恰当建议 → Thinker 下轮注入修正指导
为什么不选 Stimm BeforeSpeak 同步否决：等 Thinker 判断 = +1-3s 延迟，废掉 Speaker 的速度优势。
风险窗口：Speaker 说完到 Thinker 发现之间有 1-3s 窗口期。但 Doubao Lite 有安全对齐 + prompt 红线 + 关键词兜底，真正漏网的概率极低。灰色地带问题（不恰当建议等）由 Thinker 下轮修正，可接受。
核心参考: Stimm BeforeSpeakMessage 否决权思路（简化为异步）
