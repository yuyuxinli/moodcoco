术语速查

Embedding（向量化）
把一句话变成一串数字（向量），这样计算机可以用数学方法比较两句话的"意思有多接近"。
语义缓存（SemanticCache）
一个"临时记忆区"，Slow 提前把可能用到的资料存在这里，Fast 需要的时候直接拿，不用重新去搜。用"意思相近"（而非完全匹配）来查找。
向量数据库（VectorStore）
所有文档的"仓库"。搜索一次大约要 110ms。语义缓存就是为了避免每次都来这里搜。
FAISS
Facebook 开源的向量搜索引擎。在这个项目里既用于向量数据库，也用于语义缓存内部的快速查找。
缓存命中 / 未命中
命中：语义缓存里有需要的资料，直接拿（<1ms）。未命中：没有，得去向量数据库搜（~110ms），慢 300 多倍。
TTL（过期时间）
缓存条目的"保质期"，默认 300 秒。过期自动丢弃，防止旧资料干扰。
LRU（最久没用的先丢）
缓存满了时的淘汰策略：把最长时间没被读取过的条目删掉，给新内容腾位置。
事件总线（ConversationStream）
一条"广播频道"。发布方丢消息进去，所有订阅者都能收到。Fast 和 Slow 通过它感知对话进展，但彼此不直接通信。
STT / TTS
STT = 语音转文字（Speech-to-Text）。TTS = 文字转语音（Text-to-Speech）。
RAG（检索增强生成）
先从资料库搜出相关内容，再连同用户问题一起喂给 LLM，让回答有据可依而非纯靠"脑补"。

核心思想：趁用户还在说话，偷偷去备课

一句话总结：Slow Thinker 是一个永远在后台跑的助手。它一边听对话，一边用 LLM 猜"用户接下来可能聊什么"，然后提前把相关资料找出来，放到语义缓存里。等用户真的开口时，Fast Talker 直接从缓存拿资料（不到 1 毫秒），不需要临时去搜索。

类比：就像一个厉害的助教——老师在讲台上答学生问题（Fast），助教在后面悄悄翻书，把下一个可能被问到的内容提前夹好书签（Slow）。老师需要引用的时候直接翻到那一页，不用现翻。

语义缓存：Fast 和 Slow 之间唯一的桥梁

一个精妙的设计：资料存入缓存时，用的是资料本身的向量（而不是"是谁搜到它的"那个查询的向量）。

为什么这样做？假设 Slow 猜"用户可能问定价"，搜出了一篇"企业版定价文档"。但用户实际问的是"大客户怎么买"。如果用"定价"这个查询的向量做 key，"大客户怎么买"可能搜不到它。但如果用文档本身的向量做 key，只要文档内容和用户问题意思相近（"企业版定价"和"大客户怎么买"语义接近），就能命中。

🔮 写入方（Slow 备课员）

  • 从向量数据库搜到文档
  • 用文档自身的向量作为缓存 key 存入
  • 保质期默认 5 分钟，过期自动清
  • 内容太相似的自动合并（相似度 > 95% 视为同一条）

⚡ 读取方（Fast 快嘴）

  • 把用户的问题变成向量
  • 在缓存里按"意思相近"搜索，取最相关的 5 条
  • 搜索耗时不到 1 毫秒
  • 相似度 > 0.75 才算命中，低于此视为"没找到"

与 moodcoco 快慢思考的对比

对比维度 VoiceAgentRAG moodcoco
Slow 在做什么 猜用户下一步问什么 → 提前把资料搜好 理解用户情绪 → 选合适的心理学 skill → 注入上下文
Fast 和 Slow 怎么通信 通过语义缓存（间接，互不知道对方存在） 共享同一个 Python 对象（直接，Slow 改了 Fast 立刻能看到）
Slow 活多久 整个会话期间永远在跑 用户每说一句话创建一次，说完就结束
怎么实现并行 事件驱动：Slow 订阅事件总线，有事就干 同时创建两个异步任务
Slow 的结果什么时候生效 上一轮预存 → 这一轮缓存命中（75% 概率） 如果 Slow 比 Fast 快 → 本轮就能用上；否则下一轮
Fast 是什么形态 查缓存 → 调一次 LLM → 完事 Agent 循环：LLM → 调工具 → LLM → 调工具 → … 直到它自己决定停
核心差异：

VoiceAgentRAG 的 Slow 是「预测未来」——猜用户接下来可能聊什么，提前备好资料。
moodcoco 的 Slow 是「理解当下」——理解用户现在的情绪状态，选择合适的心理学策略。

两种模式可以结合：Slow 既理解当下（选 skill 注入本轮），又预测未来（预加载下一轮可能需要的 skill）。
