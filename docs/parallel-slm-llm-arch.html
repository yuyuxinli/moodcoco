SLM + LLM 并行降延迟 — WebRTC.ventures, 2025.06

小模型先顶上、大模型后补位 · LiveKit Agents · 感知延迟从 900ms 降到 329ms
原文：webrtc.ventures · 作者：Alberto Gonzalez

术语速查

SLM（小语言模型）
Small Language Model，参数量小、推理快、质量一般。本文用 SmolLM2-135M，只有 1.35 亿参数，TTFT 约 329ms。用来"先说一句顶住"。
LLM（大语言模型）
Large Language Model，参数量大、推理慢、质量高。本文用 OpenAI GPT 系列，TTFT 约 900ms。用来"后面补上高质量回复"。
TTFT（首 token 时间）
Time To First Token，从请求发出到模型吐出第一个字的时间。直接决定用户感知延迟。SLM 快 = 用户更早听到回应。
LiveKit Agents
基于 WebRTC 的开源实时通信框架的 Agent SDK。提供 VAD、STT、TTS 集成和会话管理，是本文方案的运行框架。
轮次检测（Turn Detection）
用小模型（而非纯 VAD）判断"用户是否说完了"，比纯静音检测更准，但会增加 100-200ms 延迟。
Chat Context
对话上下文——之前说过什么。SLM 的快回复不加入上下文（防止低质量内容污染），只有 LLM 的正式回复才加入。

核心思想

用户说完后，同时启动两个模型：

SLM 快车道 小模型 329ms 就开口，先说一句简短回复（"好的，让我帮你查一下"）让用户知道系统在响应。

LLM 慢车道 大模型 900ms 后才就绪，但生成高质量完整回复。SLM 说完后 LLM 接上，用户感知延迟降低约 60%。

核心代码逻辑

文章给出的 Python 代码片段（基于 LiveKit Agents SDK），展示并行调用的实现。 

# 创建一个 Future 来捕获 SLM 完整回复
fast_llm_fut = asyncio.Future[str]()

async def _fast_llm_reply() -> AsyncIterable[str]:
    filler_response: str = ""
    async for chunk in self._fast_llm.chat(
        chat_ctx=fast_llm_ctx    # SLM 用截断的上下文
    ).to_str_iterable():
        filler_response += chunk
        yield chunk              # 逐 token 流式输出 → TTS
    fast_llm_fut.set_result(filler_response)

# SLM 回复流式播放，但不加入对话上下文
self.session.say(
    _fast_llm_reply(),
    add_to_chat_ctx=False   # ← 关键！不污染历史
)

# 等 SLM 说完，同时 LLM 在另一个协程中并行生成
filler_response = await fast_llm_fut

SLM 配置要点

  • 截断上下文：只给最近几轮，减少输入 token
  • 低 temperature：更确定性，避免乱说
  • 专用 prompt："请给出简短的初步回应"
  • 不入上下文：add_to_chat_ctx=False

LLM 配置要点

  • 完整上下文：包含所有历史对话
  • 标准 temperature：正常推理
  • 正式回复：SLM 说完后接上
  • 入上下文：作为正式 assistant 消息记录

对 moodcoco 的启发

moodcoco 已有类似架构：Fast Agent 快回复 + Slow Agent 深度分析。 本文方案是这个思路的最简工程实现——不需要自定义训练，只需要 asyncio 并发调两个模型。

直接可借鉴的

  • add_to_chat_ctx=False 思路：moodcoco 的 Fast 快回复也不应该污染 Slow 的深度分析上下文
  • SLM prompt 设计："给出简短初步回应"——情绪场景可以是"先表达共情和倾听"
  • Grafana 可观测性：监控 TTFT / TTS 首字节 / 总感知延迟，找到实际瓶颈

moodcoco 的差异化

  • Slow 不只是"更好的回复"——还做策略选择（选哪个 Skill）、情绪判断、模式识别
  • Fast 不只是"填空"——通过 Slow 注入的上下文，Fast 的回复质量可以接近 LLM 水平
  • 跨轮记忆：Slow 的分析结果 carryover 到下一轮，本文方案没有
本质区别：本文的 SLM 是"用低质量换低延迟"——SLM 回复就是比 LLM 差，这是已知的代价。 moodcoco 的 Fast Agent 则是"用 Slow 注入的高质量上下文，让 Fast 的回复也有质量"——不是降级，而是提前准备。 这是更高级的并行策略。
