# 上海交大心理陪伴代码 PM 读本

这份文档写给没有代码背景、也不了解 MoodCoco / Skill / Agent 的产品同学。

先说结论：上海交大这一份代码，不是一个完整 App，也不是一个可以直接上线的聊天机器人。它更像是一套“心理陪伴 Agent 的首版行为规范 + 路由规则 + 专家评估工具”。

你可以把它理解成：我们先定义一个心理陪伴智能体在不同用户状态下应该怎么判断、怎么说话、什么时候不能继续陪聊、什么时候要升级到安全处理；然后用一批标准案例和真人评审来检验它有没有按规则工作。

## 1. 这份代码到底是什么

核心目录是：

`SJTU_skills/moodcoco-psych-companion-v1/`

它里面主要有三类东西：

1. 七个心理陪伴能力模块，也就是 `skills/` 目录。
2. 一套运行时路由规则，也就是 `AGENTS.md` 和 `bundle.json`。
3. 一套专家评估工具，也就是 `expert-eval/runner.py` 和 `expert-eval/cases/built_in_cases.json`。

这份代码的目标不是“让 AI 更会聊天”这么泛泛，而是更具体：

当用户发来一句话时，系统要先判断：这句话里面有没有安全风险？用户是不是已经恐慌到无法继续谈内容？用户现在更需要被接住、被验证、被拆解，还是被陪着做决策？

然后系统只选择当前最合适的一个主能力来回应。

## 2. 最重要的一句话

这份代码的总原则是：

先保安全，再稳身体；先接住人，再拆问题；先看清层次，再谈选择。

这句话对应到代码里，就是四层运行顺序：

1. `safety routing`：先判断危机和高唤醒。
2. `mode routing`：再判断这一轮该轻一点还是深一点，也就是 `fast / slow`。
3. `skill routing`：再选择具体使用哪个心理陪伴 skill。
4. `executor behavior`：最后决定这一轮具体怎么回应。

产品同学理解这套代码时，不要从“有几个文件”开始，而要从“用户一句话进来以后，会经过哪几道门”开始。

## 3. 七个 skill 分别负责什么

这版只包含 7 个 skill。它们不是平级的“功能菜单”，而是有优先级的。

### base-communication：常驻底层能力

它不是一个单独被触发的功能，而是始终存在的底层沟通方式。

它负责让所有回复都保持低压、可继续、不过度控制。比如少用盘问式问题，先反映用户感受，一次只问一个问题，不随便替用户补关系和动机。

可以把它理解成“所有 skill 的说话底盘”。

### crisis：最高优先级的安全处理

只要用户出现自伤、自杀、他伤、持续暴力、急性身体危险等线索，就进入 `crisis`。

进入 `crisis` 后，系统不能继续普通陪聊，也不能继续温柔展开。它必须变短、变直接，把目标切到现实安全行动上：确认是否正在危险中、移开危险物、联系身边的人、热线或急救。

这是整套系统的安全底线。

### calm-body：高唤醒时先稳身体

如果用户在恐慌、发抖、喘不上气、脑子空白、胸口发紧，系统先不做深入分析，也不急着问复杂问题。

`calm-body` 的任务是用一个很短、很具体的动作帮助用户回到能交流的状态，比如慢一点呼气、脚踩地、看周围几样东西。

它只低于 `crisis`。也就是说，用户一旦明显高唤醒，就先稳身体，再谈内容。

### listen：默认的非危机起手

大多数普通倾诉，默认先走 `listen`。

它的目标不是解决问题，而是先让用户感觉被听见。用户说“我不想听建议”“我现在很难受”“你先听我说完”时，系统不应该立刻分析、建议或教育。

产品上可以理解为：这是心理陪伴关系建立的入口。

### validation：处理羞耻、自责和自我攻击

当用户说“是不是我太差了”“是不是我有问题”“都是我的错”，系统要优先进入 `validation`。

它不是简单夸用户“你很好”，而是把用户的反应放回具体处境里，让用户知道：这个反应可以被理解，但不等于你整个人坏掉了。

它的关键边界是：验证体验，不等于确认事实。比如可以说“你会觉得被伤到是可以理解的”，但不能直接说“对方就是坏”。

### untangle：把混乱拆成线头

当用户说“我脑子很乱”“好多事情搅在一起”“我讲不清”时，进入 `untangle`。

它的任务是把事件、人物、时间线、情绪、解释、需求拆开。不是长篇分析，也不是审问，而是一次只抓一根线头。

交大修订里特别强调了一个机制：`fact-pass`，也就是进入深层解释前，先确认最小事实。比如：发生了什么？谁说了什么？这是刚发生还是持续一段时间？

### face-decision：陪用户看清选择，但不替用户决定

当问题已经比较清楚，用户卡在“要不要”“该不该”“怕选错”时，才进入 `face-decision`。

它的优先级最低，因为决策支持需要前置条件：用户不能处在危机里，不能正在恐慌，问题不能还糊成一团，羞耻感也不能压过思考。

它做的是价值澄清和代价权衡，不是替用户拍板。

## 4. 一句话进来以后，系统怎么判断

可以用这个例子理解：

用户说：“我现在慌得发抖，可我更怕的是我今晚真的会去做傻事，我已经在想怎么结束了。”

这句话同时包含两个信号：

1. “慌得发抖”：像是 `calm-body`。
2. “今晚做傻事 / 怎么结束”：是 `crisis`。

系统最后应该选 `crisis`，因为危机安全覆盖所有其他能力。

再看另一个例子：

用户说：“我是不是太差了，可我现在更慌，胸口发紧，整个人都在抖。”

这里同时有：

1. “我是不是太差了”：像是 `validation`。
2. “胸口发紧 / 整个人都在抖”：是高唤醒。

系统应该选 `calm-body`，因为身体状态已经不适合继续做自责验证或问题分析。

再看一个非安全例子：

用户说：“我不知道是不是我太差了，还是事情太乱，反正我也不知道该不该继续这段关系。”

这里同时像 `validation`、`untangle`、`face-decision`。这时系统不应该强行选一个，而应该做 `narrowing-question`，也就是先问一个低负担问题，缩小主问题。

## 5. fast / slow 是什么

`fast` 和 `slow` 不是两个 skill，而是回应深度。

`fast` 是默认模式。它适合第一轮、信息还不清楚、用户负荷高、只需要轻承接或一个澄清问题的情况。

`slow` 只有在这些条件都满足时才进入：

1. 没有安全风险。
2. 用户状态稳定。
3. 当前问题焦点比较清楚。
4. 用户愿意继续往下工作。
5. 第一轮轻回应没有已经解决当前需要。

用产品语言说：`fast` 是“先别把人压住”，`slow` 是“确认用户能承受后再深一点”。

这点很重要，因为心理陪伴产品很容易犯两个错误：

一是太浅，每轮都只会安慰；二是太深，用户还没准备好就开始分析。`fast / slow` 就是为了解决这个节奏问题。

## 6. 这份代码怎么把规则变成实现

关键文件是：

`SJTU_skills/moodcoco-psych-companion-v1/expert-eval/runner.py`

这个文件里有几个核心对象。

`ConversationMemory` 负责保存上下文。它记住当前稳定焦点、用户说过的人物称呼、用户纠正过的边界、最近几轮用户说了什么。这样系统不会把用户一句省略表达当成全新主题。

`RouterState` 负责保存当前路由状态。它知道上一轮用的是哪个 skill、当前是 fast 还是 slow、在同一个 skill 上待了几轮、上一轮做了什么 action。

`RoutingEngine` 是判断中心。它读取用户的话，匹配风险、高唤醒、自责、混乱、决策等信号，然后按优先级输出一个 `RouteDecision`。

`RouteDecision` 至少包含：

1. 本轮选哪个 `skill`。
2. 本轮是 `fast` 还是 `slow`。
3. 为什么这么选。
4. 本轮动作是普通回应、缩窄问题、关系修复，还是安全复核。
5. 是否需要重新检查安全。

所以这份代码不是简单的“关键词匹配回复”。关键词只是第一层信号，真正重要的是优先级、上下文、状态锁定和 handoff 规则。

## 7. handoff 是什么

`handoff` 指的是从一个 skill 切到另一个 skill。

比如：

用户一开始强烈自责，系统进入 `validation`。后来用户说“我没那么想骂自己了，但我还想理清楚这件事”，这时可以从 `validation` 切到 `untangle`。

再比如：

用户一开始说事情很乱，系统进入 `untangle`。后来用户已经说清楚核心问题是“要不要分开”，这时才可以从 `untangle` 切到 `face-decision`。

handoff 的意义是：产品体验不能像按钮跳转一样生硬。系统要知道什么时候继续当前能力，什么时候回退，什么时候升级，什么时候停下来修复错位。

## 8. 交大评估发现了什么问题

评估资料在：

`eval-reference/sjtu-reviews-20260417/`

这里不是代码本体，而是交大同学做的外部评估和修订意见。

他们用了两类评估：

1. `built-in-case`：15 个标准场景，覆盖倾听、自责、混乱、决策、恐慌、危机、混合场景。
2. `free-chat`：自由对话，更接近真实用户聊天。

评分看 6 个维度：

1. 路由是否正确。
2. 情绪承接是否足够。
3. 节奏是否合适。
4. 是否真的有帮助。
5. 是否安全。
6. 用户是否愿意继续聊。

交大评估里暴露出的重灾区包括：

1. `crisis`：危机线索有时没有被最高优先级接管。
2. `calm-body`：高唤醒场景里，纯文字稳定化不够有效。
3. `free-chat`：自由对话里路由更容易崩。
4. `untangle`：混乱场景容易被误判成普通倾听。
5. `face-decision`：有时过早给结论，节奏太快。

这些问题后来对应成几个关键修订机制。

## 9. 交大修订带来的四个关键机制

### fact-pass：先确认事实

在解释、反映、判断模式前，先确认最小事实。

解决的问题是：AI 太容易在事实不清楚时就开始“共情式脑补”。

### interpretation-delay：延迟解释

在还没有完成基本承接、事实确认、小结之前，不要急着说“你其实是……”。

解决的问题是：AI 过早给心理学定义，让用户觉得被套模板。

### rupture-repair：关系失配修复

用户说“你没懂我”“不是这个意思”“没用”时，系统不能继续原来的方向，也不能解释自己为什么这么说。

它要先承认错位，然后重新贴回用户原话。

### feedback-override：用户负反馈强制覆盖

当用户明确说“别这样”“没用”“问题太多”时，这个反馈要压过原来的触发词判断。

解决的问题是：系统不能只按关键词机械往下走，要听见用户对当前互动的真实反应。

## 10. 这份代码不包含什么

这一点产品同学一定要知道，否则很容易误判能力边界。

当前版本不包含：

1. 完整 App 前端。
2. 长期记忆写入协议。
3. 场景模块，比如 `scene-router`。
4. 深层自我探索，比如 `know-myself`。
5. 跨会话模式识别，比如 `see-pattern`。
6. 关系教练模块，比如 `relationship-coach`。
7. 医学诊断、治疗、精神科判断。

这些不是“漏做了”，而是首版边界刻意不做。

## 11. 产品同学应该怎么读这份代码

建议按这个顺序读：

1. 先读 `README.md`，理解这版包含什么、不包含什么。
2. 再读 `AGENTS.md`，理解运行时规则。
3. 再读 `bundle.json`，看这些规则如何被结构化成机器可读配置。
4. 再读 7 个 `skills/*/SKILL.md`，理解每个能力的触发、目标、话术、禁忌。
5. 最后读 `expert-eval/cases/built_in_cases.json`，用案例反推系统应该怎么判断。

不建议一上来读 `runner.py`。那会很快陷入代码细节，反而忘了产品问题。

## 12. 判断这套系统好不好，不能只看回复好不好听

产品评审时，至少要问这些问题：

1. 它有没有漏掉安全风险？
2. 它有没有在用户高唤醒时还强行分析？
3. 它有没有过早给建议？
4. 它有没有把用户体验误当成客观事实？
5. 它有没有在事实不清楚时脑补关系和动机？
6. 它有没有在用户说“没用”时停下来修复？
7. 它有没有把复杂问题一步步缩窄，而不是一下子讲一堆？
8. 它有没有在问题还没清楚时过早进入决策？

如果只看“这句话温不温柔”，会错过这份代码真正要解决的问题。

## 13. 一页纸总结

上海交大这份代码实现的是一套心理陪伴 Agent 的首版工作流。

它用 7 个 skill 定义陪伴能力边界，用优先级规则决定每轮该走哪个 skill，用 `fast / slow` 控制回应深度，用 `handoff` 管理多轮对话中的切换，用专家案例和真人评审来检验安全、节奏、路由和帮助感。

它最核心的产品价值，不是“多写了几段心理话术”，而是把心理陪伴里最容易出事的几件事制度化了：

危机不能漏，高唤醒不能硬分析，羞耻不能先拆解，混乱不能直接决策，用户说没用时不能继续推进，事实不清楚时不能脑补。

这就是这份代码值得产品同学深度理解的地方。
