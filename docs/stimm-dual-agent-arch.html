术语速查

VoiceAgent（前台 Agent）
快速路径。拥有实时音频管线 VAD→STT→fast LLM→TTS，负责即时对话。延迟优先，用小/快模型（如 gpt-4o-mini）。
Supervisor（后台监督者）
深度路径。以 data-only 参与者加入 LiveKit room（无音频），接收实时转写，执行深度推理/工具调用/规划，通过 data channel 发送指令。
Steering Instruction
Supervisor 发给 VoiceAgent 的操控指令。包含上下文注入、语音中断、模式切换、回复覆盖等 5 种消息类型。
Optimistic VUI
核心理念：先开口再纠正。VoiceAgent 先用快模型说一句过渡性回答，Supervisor 的深度结果到达后再注入补充或纠正。
StimmProtocol
VoiceAgent 和 Supervisor 之间的通信协议。基于 LiveKit reliable data channel，JSON 序列化，topic 为 "stimm"。
Operating Mode
VoiceAgent 的三种工作模式：autonomous（自主）、relay（中继，只说 Supervisor 给的内容）、hybrid（默认，先自主再纳入 Supervisor）。
LiveKit Room
WebRTC 实时通信房间。VoiceAgent 和 Supervisor 都加入同一个 room，但 Supervisor 只走 data channel，不占音频轨道。

核心思想

前台 Agent 负责说话节奏，后台 Supervisor 负责质量、工具和纠错。
VoiceAgent 用快模型即时回复用户（保证低延迟），Supervisor 在后台做深度推理和工具调用， 然后通过 data channel 发送 steering instructions 来远程操控 VoiceAgent 的行为——注入上下文、替换回复、切换模式、甚至中断当前语音。
类比：电视直播主播（VoiceAgent）戴着耳机，导演（Supervisor）在幕后通过耳机告诉主播： "观众问的这个问题，答案是…"、"切换到下一个话题"、"现在停下来，说这句话"。

StimmProtocol 消息详解

VoiceAgent 和 Supervisor 通过 LiveKit data channel 交换 JSON 消息。协议定义了 4 种上行 + 5 种下行消息类型。

VoiceAgent → Supervisor（4 类）

消息内容
TranscriptMessage 实时 STT 输出（partial + final），含 confidence
StateMessage Agent 状态变化：listening / thinking / speaking
BeforeSpeakMessage TTS 前触发，含 turn_id，给 Supervisor 审核窗口
MetricsMessage 每轮延迟指标：VAD/STT/LLM TTFT/TTS TTFB/total

Supervisor → VoiceAgent（5 类）

消息内容
InstructionMessage 说话指令，priority=interrupt 可中断当前语音
ContextMessage 注入上下文到 Agent 工作记忆（append / replace）
ActionResultMessage 工具/动作执行结果通知（如 calendar_check → done）
ModeMessage 动态切换模式：autonomous / relay / hybrid
OverrideMessage 按 turn_id 取消待发语音并替换内容

三种工作模式

Autonomous
VoiceAgent 完全自主回复。
Supervisor 指令可选保存但不强制执行。
适合：简单闲聊、不需要深度推理的场景。
Hybrid（默认）
先自主生成快速回复，
Supervisor 结果到达后纳入后续回复。
适合：大多数对话——低延迟 + 高质量两手抓。
Relay
VoiceAgent 只说 Supervisor 给的内容。
完全受控模式。
适合：需要严格控制输出的场景（医疗、法律）。
模式可以动态切换：Supervisor 通过 ModeMessage 实时改变 VoiceAgent 的模式。 例如：日常对话用 hybrid，检测到用户提到敏感话题时切换到 relay，确保每句话都经过 Supervisor 审核。

Steering 事件时间线

Hybrid 模式下，一次典型的 "先快后深" 交互流程：

用户问了一个需要查数据库的问题
T0
🎤 用户说话 "帮我看下明天下午有没有空？"
T1
⚡ VoiceAgent 即时回复 Fast LLM 生成过渡回答："好的，我帮你查一下明天的日程。"
（同时通过 data channel 把 transcript 发给 Supervisor）
T2
🧠 Supervisor 后台处理 调用日历 API 查询明天下午的空闲时间 → 得到结果：14:00-16:00 空闲
（返回 TRIGGER 决策 + ActionResultMessage）
T3
📡 Steering: ContextMessage Supervisor 注入上下文："用户明天 14:00-16:00 空闲，其余时间有会议"
VoiceAgent 的 Fast LLM prompt 被更新
T4
⚡ VoiceAgent 后续回复 基于注入的上下文生成："查到了，你明天下午两点到四点是空的，其他时间都有会议。要帮你约吗？"
关键设计：VoiceAgent 的 Fast LLM prompt 被要求"将 Supervisor 最新消息视为唯一权威事实来源"。 如果 Supervisor 还没给结果，Fast LLM 会说"我需要查一下"——不会编造事实。

技术实现细节

运行时架构

  • 基于 livekit-agents ≥ 1.1 构建
  • Python 3.10+，Pydantic v2 序列化
  • Supervisor 有两种基类：Supervisor（裸事件处理）和 ConversationSupervisor（内置滚动历史 + 静默检测 + JSON 决策契约）
  • 支持 23 种 STT / 28 种 TTS / 21 种 LLM 后端
  • Docker Compose 一键部署

防重复与延迟触发

  • 静默等待：Supervisor 等用户沉默 2.5s 后才处理（避免碎片化调用）
  • 去重冷却：同一指纹的 context 在 8s 内不重复触发
  • 延迟注入：如果 Agent 正在说话，context 注入延迟到空闲时（每 0.5s 重试）
  • 滑动窗口：VoiceAgent 只保留最近 5 条 Supervisor 指令
  • Pre-TTS 缓冲：token 先缓冲再送 TTS，平衡延迟和自然度

对 moodcoco 的启发

✓ 可以借鉴的

  • 消息化 Steering 替代共享对象——Stimm 的 StimmProtocol 是 moodcoco slow_inject_to_fast / slow_set_fast_retrieval 的解耦版本。消息化设计使 Supervisor 可以独立部署甚至用不同语言实现
  • BeforeSpeak 审核窗口——TTS 前让 Supervisor 审核/覆盖，对情绪安全边界很有价值：Slow 检测到风险内容时可以在出声前拦截
  • 三种模式动态切换——日常用 hybrid，敏感话题切 relay（Slow 全权控制），简单闲聊切 autonomous（节省 Slow 算力）
  • 结构化决策契约——Supervisor 返回 NO_ACTION / TRIGGER JSON，比 moodcoco 当前的非结构化注入更清晰

⚠ 需要注意的

  • 项目较早期——43 stars，单人开发，2026 年 3 月后活跃度下降。不适合直接依赖，但架构设计值得参考
  • Supervisor 等 2.5s 才处理——对情绪陪伴场景太慢，用户说完后期望立即得到共情回应而非等 2.5s 静默
  • 没有发布性能基准——只有 MetricsMessage 基础设施，无公开延迟数据，实际性能未知
  • 网络通信开销——data channel 在同机部署时开销可忽略，但分布式部署增加 10-50ms 延迟
最值得借鉴的设计模式：
Stimm 的 "Optimistic VUI" + 消息化 Steering 是 moodcoco Fast/Slow 架构的工程化方向。 当前 moodcoco 的 Slow 通过 Python 对象突变注入 Fast（slow_inject_to_fast），如果要支持 Slow 独立部署（如 GPU 服务器上运行大模型）、 或支持多种 Supervisor 策略热切换，就需要 Stimm 这种协议化设计。

第一步建议：不需要引入 LiveKit data channel 全套协议。先在现有 Fast/Slow 之间定义 JSON 消息契约（TRIGGER / NO_ACTION / INJECT）， 替代直接 Python 对象操作。这是最小成本的解耦改造。
