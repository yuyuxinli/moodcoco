先别看模块。先看这 8 个零件。

你现在已经懂了最表层：用户输入一句话，AI 回一句话。真正卡住的地方是：这中间被偷偷塞进了 8 个知识点。我们不跳步，一个一个加。

你看到的 vs 系统实际做的
用户输入一句话
→
AI 回一句话
把中间放大以后
用户说出一句自然语言
代码先做分诊：这句话像哪类情况
代码选 skill / mode / action
规则包把上交同学写好的规则塞进去
大模型按这些限制写出最终回复
Part 1

这不是 1 个知识点，是 8 个零件。

把它想成一台机器。每个零件都很简单，但它们拼起来以后，才会变成你看到的“AI 回复”。

人输入 代码判断 规则材料 大模型写作
1用户

用户输入

就是用户在 ChatBox 里打的那句话。它通常很自然、很乱、很口语。

像一个人走进前台说：“我现在很乱，不知道怎么办。”
2代码

代码

代码不是 AI。它不负责温柔地聊天，只负责按固定流程检查信号。

像前台分诊员：不治疗，只先判断该去哪一队。
3代码

判断情况

不是深刻理解人生，而是先分类：危机？恐慌？自责？混乱？决策纠结？

像看症状标签：发烧、胸闷、外伤，先分清轻重缓急。
4规则

skill

skill 是“应对方式”。比如先听、先稳身体、先处理风险、先理线头。

像科室：急诊、呼吸调整、倾听、拆问题、看选择。
5代码

mode

mode 是“这一轮要说多深”。fast 轻一点，slow 才深入一点。

像老师讲题：先给提示，还是展开完整推导。
6代码

action

action 是“这一轮具体做什么”。正常回应、问一个缩窄问题、检查安全、修复错位。

像下一步动作：问一句、先停下、转急救、重新确认。
7规则包

拼提示词

大模型不只看到用户原话。代码会把用户话、路由结果、skill 规则一起打包。

像把病历、分诊结果、注意事项放进一个文件夹。
8大模型

最终回复

大模型负责把前面选好的方向，写成用户能读懂的一句话或一段话。

像会表达的人，拿着工单写出最终对话。
Part 2

现在把 8 个零件一层层拼起来。

你可以先只看左边的步骤。右边是同一个例子如何一步步从“用户一句话”变成“AI 回复”。

1

用户先说一句话

这是唯一真正来自普通用户的输入。

2

代码像分诊台一样检查

它先看有没有高优先级信号，比如风险或高唤醒。

3

代码选 skill

如果用户说“脑子很乱”，通常不是先做决定，而是先 untangle。

4

代码选 mode

第一轮通常 fast：短一点、轻一点，不要马上长篇分析。

5

代码选 action

如果信号混在一起，就先 narrowing-question，只问一个缩窄问题。

6

代码打包提示词

把用户原话、路由决定、上交同学写好的 skill 规则一起给大模型。

7

大模型写回复

它不是自由发挥，而是在这些限制下写自然语言。

8

用户看到 AI 回复

用户只看到最后一句，但看不到中间这些判断。

同一个例子：一步步拼装
用户话
“我现在脑子很乱，也不知道该不该继续这段关系。”
代码检查
没有明显危机；没有明显恐慌；有“脑子很乱”；也有“该不该”。
skill
优先 untangle，因为问题还混在一起，不适合直接 face-decision。
mode/action
fast + narrowing-question：轻一点，只问一个缩窄问题。
最终回复
“我先不急着帮你做决定。我们先抓一根线：现在更卡你的是事情太乱，还是已经在两个选择之间拉扯？”
Part 3

最关键的问题：谁在做决策？

这件事一定要讲清楚：在这个评估代码里，路由主要是代码在做；大模型主要是在路由结果出来后负责写回复。

代码负责：像分诊台
检查用户话里有没有风险、高唤醒、自责、混乱、决策纠结。
按照优先级选 skill，比如 crisis 高于 calm-body，高于 listen。
决定 mode：这一轮 fast 还是 slow。
决定 action：正常回应、缩窄问题、安全复核、修复错位。
大模型负责：像表达者
读代码打包好的提示词。
遵守被选中的 skill 规则。
把“应该怎么做”写成自然、能被用户接受的话。
它写最终回复，但不应该自己随便换路线。
费曼版一句话：代码决定“这轮该往哪儿走”，大模型决定“这句话怎么说出来”。
Part 3.5

源码拆解：这里说的“代码”到底是什么？

这里的“代码”主要指 `expert-eval/runner.py`。它不是聊天 UI，也不是大模型本身。它像一个评测运行器：读规则、读用户输入、做路由、拼提示词、调用 MiniMax。

1. 信号表：代码先看关键词 runner.py · SIGNAL_LIBRARY

源码里有一张“信号表”。它把用户话里的词，先粗分成危机、高唤醒、自责、混乱、决策等类别。

SIGNAL_LIBRARY = {
  "crisis": ["不想活", "想死", "自杀", "做傻事", "家暴"],
  "calm-body": ["心慌", "发抖", "喘不过气", "脑子空白"],
  "validation": ["是不是我太差", "都是我的错", "我真没用"],
  "untangle": ["我脑子很乱", "讲不清", "搅在一起"],
  "face-decision": ["不知道怎么选", "要不要", "该不该"]
}

费曼版：这不是“理解全部人生”，而是先贴标签。像急诊台先问：流血吗？胸痛吗？能呼吸吗？

2. 路由结果：代码输出一张小工单 runner.py · RouteDecision

判断完以后，代码不会直接写回复。它先产出一张“本轮该怎么做”的小工单。

RouteDecision(
  skill="untangle",
  mode="fast",
  action="narrowing-question",
  reason="问题混杂，先理线头",
  recheck_safety=False
)

费曼版：医生还没开口安慰你，前台先在单子上写：去哪个科、急不急、下一步做什么。

3. 判断顺序：代码不是平等比较 runner.py · decide()

路由最关键的是顺序。危机永远先看，然后才是高唤醒，再往后才是普通陪伴 skill。

def decide(user_text, state):
  signals = collect_matched_signals(user_text)

  if crisis_lock_active:
    return skill="crisis", action="safety-recheck"
  if crisis_match:
    return skill="crisis"
  if calm_body_lock_active:
    return skill="calm-body"
  if calm_match:
    return skill="calm-body"
  if feedback_override:
    return action="repair-then-reroute"
  if validation + untangle + decision 重叠:
    return action="narrowing-question"
  ...

费曼版：不是“哪个词看起来多就选谁”，而是先问“哪个问题最不能漏”。

4. skill 文案：上交同学写的规则在哪里 skills/*/SKILL.md

每个 skill 都是一份规则说明。比如什么时候用、目标是什么、禁忌是什么、可以怎么说。

skills/
  listen/SKILL.md
  validation/SKILL.md
  untangle/SKILL.md
  face-decision/SKILL.md
  calm-body/SKILL.md
  crisis/SKILL.md
  base-communication/SKILL.md

费曼版：skill 不是一段神奇代码，而是“这类情况应该怎么处理”的操作手册。

5. 提示词拼装：把规则装进大模型输入 runner.py · build_system_prompt()

这一步把常驻 skill、当前 skill、路由原因、mode、action、上下文记忆都拼成 system prompt。

base_skill = load_skill_text("base-communication")
routed_skill = load_skill_text(route.skill)

prompt = f"""
当前主 skill 是 {route.skill}
当前 mode 是 {route.mode}
当前 action 是 {route.action}
当前路由原因：{route.reason}

=== ALWAYS ON ===
{base_skill}

=== CURRENT PRIMARY SKILL ===
{routed_skill}
"""

费曼版：不是大模型自己去翻所有规则，而是代码把“本轮该看的那几页”夹好递过去。

6. 大模型调用：最后才轮到模型写话 runner.py · minimax_chat()

模型配置在代码里。这里用的是 MiniMax 接口，模型名、温度、输出上限会影响表达，但不等于路由规则。

DEFAULT_CONFIG = {
  "model": "MiniMax-M2.5",
  "temperature": 0.7,
  "max_tokens": 1600
}

payload = {
  "model": config["model"],
  "messages": messages,
  "temperature": config["temperature"],
  "max_tokens": config["max_tokens"]
}

费曼版：模型像“写作者”。它的文笔会受模型和温度影响，但它拿到的任务单更决定它该写什么方向。

对象
关键内容
相对不关键，或不是第一优先级
代码
信号表、优先级顺序、状态锁定、handoff、mode/action 判断。
具体文件有多长、函数名字是否漂亮，不是产品排查的第一入口。
规则
skill 的触发条件、目标、禁忌、话术边界。
话术是否很文学化不是最关键，先看边界是否清楚。
大模型
它看到的 prompt 是否包含正确路由、正确 skill、正确限制；最终回复是否遵守。
模型名和温度会影响质量，但如果路由错了，换模型通常救不回来。
评估
有没有覆盖真实失败场景；有没有检查 route_fit、pacing、safety。
只看“回复好不好听”不够，因为真正的问题可能在路由层。
一句话：这套系统不是“一个大模型在自由思考”。它更像“代码分诊 + 规则手册 + 大模型表达 + 评估复盘”的组合。
Part 4

“拼提示词”到底是什么意思？

这一步特别容易听起来玄。其实它就是把几张纸放进同一个文件夹，然后交给大模型。

交给大模型的提示词包
用户原话：我现在脑子很乱，也不知道该不该继续这段关系。
代码决定：skill = untangle，mode = fast，action = narrowing-question。
上交规则：一次只问一个问题；不要直接做决定；先理线头。
边界提醒：不要补关系设定，不要长篇分析，不要替用户下结论。
大模型看到这个包以后，才写出最后回复：

“我先不急着帮你做决定。我们先抓一根线：现在更卡你的是事情太乱，还是已经在两个选择之间拉扯？”
所以：用户看到的是一句自然回复；系统内部其实先给大模型发了一份“带规则的任务单”。
Part 5

最后，把完整链路放在一张表里。

这张表就是你后面诊断产品问题的地图。哪里坏了，就回到哪一层看。

1
用户
输入一句自然语言。它可能很短、很乱、带情绪，也可能同时包含多个信号。
2
上交同学
预先写好了规则：有哪些 skill、优先级是什么、每个 skill 应该怎么说、不能怎么说。
3
代码
读取用户输入，检查信号，先做“这句话属于什么情况”的初步分类。
4
代码
根据优先级选出 skill / mode / action。这一步是路由的核心。
5
规则包
把用户原话、路由结果、skill 文案、边界限制拼成提示词。
6
大模型
根据提示词生成最终回复。它负责表达，但方向已经被前面约束。
7
用户
只看到最终 AI 回复，看不到中间的判断、路由、提示词拼装。
8
评估
再检查刚才有没有选对 skill、节奏是否合适、安全有没有漏、用户是否愿意继续。
以后你看到一个坏回复，不要直接问“AI 怎么这么笨”。先问：是用户输入没有被正确分类？是代码路由错了？是 skill 规则写得不清？是提示词拼装错？还是大模型表达没跟上？
Part 6

总流程图：把整套机制放在一张图里。

这张图只看整体，不看细节。你可以把它当成之后排查问题的总地图。

人：输入与看到结果
上交同学：预先写规则
代码：做路由决策
大模型：写最终回复
用户输入 “我现在脑子很乱，也不知道该不该继续。”
→
代码分诊 检查危机、高唤醒、自责、混乱、决策纠结。
→
路由结果 选出 skill / mode / action。
→
大模型回复 按规则写出用户能读懂的话。
规则来源 skills、AGENTS.md、bundle.json。
→
进入提示词包 用户原话 + 路由结果 + skill 文案 + 边界限制。
评估案例 built-in cases 和 free-chat 记录。
→
回看表现 route_fit、pacing、safety、usefulness 等指标。
一句话看懂：上交同学先写“规则书”；用户说一句话；代码按规则做分诊和路由；代码把材料打包给大模型；大模型写出最终回复；评估系统再检查这次有没有走对。
