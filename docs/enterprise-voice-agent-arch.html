术语速查

STT（语音转文字）
Speech-to-Text，把用户说的话变成文字。本项目用 Deepgram 实时流式识别。
TTS（文字转语音）
Text-to-Speech，把 AI 回复变成声音。本项目用 ElevenLabs，按句子逐条合成。
LLM 流式生成
大模型不是一次性输出全部文字，而是一个词一个词地"吐"出来（像打字机）。每个词叫一个 token。
断句缓冲区（SentenceBuffer）
积攒 LLM 吐出的 token，检测到完整句子（遇到句号、问号等）就立刻交给 TTS。避免把半句话送去合成。
函数调用（Function Calling）
LLM 发现需要查数据时，不直接回答，而是"调用"一个预定义函数（如查医生排班），拿到结果后再生成回复。
TTFT（首 token 时间）
Time To First Token，用户说完话到 LLM 吐出第一个字的等待时间。越短体验越流畅。
TTFA（首音频时间）
Time To First Audio，用户说完话到听到第一句回复声音的等待时间。这才是用户真正感知的延迟。
流水线重叠
核心优化：LLM 还在生成后续内容时，前面已完成的句子已经在 TTS 合成了。两个阶段在时间上重叠，而非串行等待。

核心架构：流式管线（Chapter 04）

用户说完话后，经过下面四个阶段。关键优化是阶段重叠——LLM 还在吐后续 token 的同时，已完成的句子已经在被 TTS 合成。

重叠而非串行：假设 LLM 生成了 3 句话。传统做法要等 3 句全部生成完才开始 TTS。 这里的做法是第 1 句完成就立刻送 TTS，与此同时 LLM 继续生成第 2、3 句。用户在 LLM 还没说完时就已经开始听到回复了。

断句缓冲区：流水线的桥梁

LLM 吐出的是零碎 token（"好"、"的，"、"我"、"帮"...），TTS 需要完整句子。 断句缓冲区就是这两者之间的"翻译官"。

工作原理

  • token 持续追加到缓冲区
  • 检测句末标点：. ! ? 后跟空格
  • 检测到 → 提取整句 → 送 TTS
  • LLM 结束 → flush 剩余文字

防误判机制

  • 缩写词：Dr. / Mr. / Mrs. / U.S.A. 等不算句末
  • 小数：98.6 度中的 . 不算句末
  • 最小长度：太短的片段（如 "Hi."）不单独发送，继续等后续内容
为什么不直接按固定长度切分？ TTS 在句子边界处停顿才自然。如果把 "Johnson 医生下周一有空，" 切成 "Johnson 医生下周" 和 "一有空，"， 合成的语音会在奇怪的地方断开，听起来像机器人。按语义句子切分是语音 Agent 的基本要求。

函数调用循环（Chapter 08）

当 Agent 需要查询外部数据（如医生排班）时，不能直接回答。它需要先调用工具函数，拿到数据后再生成回复。 这形成了一个循环：可能需要多轮工具调用才能收集够信息。

Agent 循环
用户输入
→
LLM 思考
→
返回 tool_call?
→
执行工具函数
→
结果喂回 LLM
↩ 如果 LLM 还需要调更多工具 → 继续循环
循环结束条件：LLM 输出文字回复（而非 tool_call）→ 流式生成 → 断句 → TTS

5 个内置工具

  • check_availability 查医生排班
  • schedule_appointment 预约挂号
  • cancel_appointment 取消预约
  • get_patient_info 查患者信息
  • get_doctor_info 查医生信息

两种模式

  • 非流式 process()：工具调用 + 最终回复都是同步完成，适合测试
  • 流式 process_streaming()：工具调用仍是同步循环，但最终文字回复切换为流式输出 → 送入断句 → TTS
关键设计：工具调用阶段不流式（因为需要完整 JSON 参数），只有最终回复阶段才流式。

核心差异： Enterprise Voice Agent 是一个教科书级的基础管线——把 STT、LLM、TTS 串起来，用断句实现流水线重叠。 它没有并行思考的概念，但它的断句缓冲区和流式管线是所有语音 Agent 的底层基础设施， VoiceAgentRAG 和 moodcoco 都需要这一层。
对 moodcoco 的启发：
  • 断句缓冲区可以直接复用——moodcoco 的 Voice Streaming 模式也需要按句子切分送 TTS
  • 工具调用阶段不流式的设计值得参考——函数调用需要完整 JSON，强行流式会增加复杂度
  • TTFA 而非 TTFT才是用户感知指标——moodcoco 应该以用户听到第一句话的时间为优化目标
